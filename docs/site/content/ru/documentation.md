# Правила документации {#documentation-contracts}

Документация F-Layer использует
[общий шаблон Fuzzy Technologies](https://github.com/Fuzzy-Technologies/FuzzyRoutines/tree/develop/docs/documentation-blueprint).
Страницы собираются с помощью MkDocs Material, а справочник Python API —
с помощью mkdocstrings-python и Griffe из установленного wheel. Настройки темы,
CSS и SVG хранятся в репозитории. Готовый HTML создаётся при сборке.

## Как собирается справочник API {#api-discovery}

Для каждого публичного модуля Python в пакете `flayer` создаётся страница API.
Модуль запуска `flayer.__main__` также включён в справочник. Внутренние модули
и вспомогательные функции остаются в исходниках; причины исключения записаны
в правилах покрытия. Анализатор читает синтаксис Python, не выполняя код пакета.
Попытка импортировать его во время анализа прерывает сборку.

Сборка сравнивает список и содержимое файлов установленного пакета с исходниками;
байткод в сравнение не входит. Для публичных определений и методов протоколов
проверяются ссылки на соответствующие разделы HTML. На каждой странице API
есть ссылка на исходный код в `develop`.

Каждый файл репозитория должен соответствовать одному правилу покрытия. Все
основные Markdown-документы — политики, руководства по выпускам, ADR, шаблоны
и вводные страницы — включаются в сайт и доступны из английского оглавления.
Для тестов, инструментов, workflow, примеров, ресурсов и конфигурации указывается
назначение; отдельные страницы API для них не придумываются. Переведённые страницы
собираются с учётом состояния проверки. Подробности описаны в
[правилах покрытия](../../../development/documentation-coverage.md).

Столбцы всех таблиц Markdown выравниваются по самой широкой ячейке, чтобы
исходный текст было удобно читать. Проверка сохраняет экранированные вертикальные
черты, код в ячейках, маркеры выравнивания и примеры в блоках кода.

Для авторских страниц ведётся реестр переводов. Для автоматически создаваемых
страниц API сборка формирует список с постоянными ID и хешами английского
текста. Наличие страницы в этом списке не означает, что она переведена или
проверена: состояние определяется по реальным переводам и записям проверки.

## Языки и проверка переводов {#language-and-review}

Английский текст служит оригиналом. По запросу владельца АИна сверяет русские
и китайские авторские страницы с оригиналом. Проверенные страницы открываются
без плашки черновика. Если перевода нет или он устарел, показывается актуальный
английский текст с уведомлением. Это правило действует и для справочника API,
и для инженерной документации.

Для каждого перевода сохраняются постоянный ID, хеш английского текста и путь
к файлу. Для одобрения нужны редакционная и техническая проверки: кто проверил,
когда проверил по UTC и какая версия текста была проверена. По
[ADR 0015](https://github.com/Fuzzy-Technologies/F-Layer/blob/v1.2.1/docs/adr/0015-accountable-ai-translation-review.md)
в F-Layer допускается проверка ИИ. В записи это указано явно; дополнительно
сохраняется хеш перевода. Такая запись не означает проверку человеком.
При изменении оригинала или перевода нужна новая проверка. Простое обновление
хеша английского текста не возвращает переводу статус одобренного.

Термины согласуются по глоссариям. История проверок хранится в реестре и отчёте
сборки.

## Публикация {#publication}

Для pull request и ветки `develop` CI создаёт файлы предпросмотра и отчёты
проверок. Только `push` в `master` публикует проверенную сборку на GitHub Pages.
Публикация документации и публикация Python-пакета выполняются отдельно.

Адреса языковых версий: `/F-Layer/en/`, `/F-Layer/ru/`, `/F-Layer/zh-CN/`.
Корневой адрес открывает английскую документацию. До появления стабильного
выпуска документация не заявляется как неизменяемая документация этого выпуска.

[ADR 0004](../../../adr/0004-documentation-platform.md)
описывает генератор, проверку переводов, хеши исходников, показ оригинала при
отсутствии перевода и правила публикации.
